01. Project Overview

Shuvo Milon is a Bangladeshi Islamic matrimonial and biodata-based matchmaking web application. It helps individuals and families discover compatible life partners through structured profiles, consent-based matching, and privacy-conscious communication.

02. Project Vision

Build a reliable digital matrimonial ecosystem where people can discover compatible life partners without compromising personal privacy, dignity, or family values.

  1. Trust: Verified profiles and responsible moderation.
  2. Privacy: Personal contact information protected by default.
  3. Consent: Private access depends on the approved mutual-consent policy.
  4. Compatibility: Structured biodata and filters support discovery.
  5. Accessibility: Bengali-first, responsive experience.
  6. Security: Strong authentication, authorization and data handling.

03. Key Features

Authentication and accounts

Phone-number registration, Firebase OTP verification, session handling and protected routes.

Matrimonial biodata

Personal, educational, professional, family, religious, lifestyle and marriage-preference information, with profile photographs and privacy settings.

Profile discovery

Browse profiles, structured search filters, detailed biodata, pagination and shortlists.

Interest and matchmaking

Send interest, review incoming requests, accept or reject, create matches after required mutual acceptance, and reveal contact details only under authorization policy.

Private communication

Conversation list, real-time messaging, access control, reporting and blocking.

Matrimonial CV

Multi-step CV forms, autosave, preview, templates and Bengali PDF output.

Administration and information

Admin roles, profile verification, report moderation, About, FAQ, Guide, Contact, Privacy, Terms and Refund pages.

4.6 Constraints and assumptions

  • A configured Firebase project is required.
  • Phone Authentication and authorized domains must be configured.
  • Cloudinary credentials are required for signed uploads.
  • Production database, billing and deployment require owner approval.
  • Third-party service availability can affect application functionality.

4.7 Acceptance criteria

  1. Authentication works in the target environment.
  2. Users can manage their own biodata.
  3. Public responses exclude private fields.
  4. Search, interests and matching use real data and enforce authorization.
  5. Contact reveal and messaging are access-controlled.
  6. Admin operations are protected.
  7. Automated tests, responsive checks and performance checks are completed.
  8. Known limitations are documented before release.

05. System Architecture

The application uses a layered architecture. The presentation layer communicates with application services. Sensitive business operations run in trusted server-side code. Firebase provides identity and database services; Cloudinary handles media.

08. Database Design

Cloud Firestore is the primary database. The conceptual domain includes users, profiles, interests, matches, chats, messages, shortlists, CVs, reports and blocks.

Firestore
├── users/{uid}
├── profiles/{uid}
│   └── private/contact
├── interests/{interestId}
├── matches/{matchId}
├── chats/{chatId}/messages/{messageId}
├── shortlists/{shortlistId}
├── cvs/{cvId}
├── reports/{reportId}
└── blocks/{blockId}
This is an illustrative collection map only. The actual paths, IDs, indexes and fields must match docs/DATA_MODEL.md. Do not migrate or rename collections based on this diagram alone.

Data management principles

  • Use authenticated user IDs for ownership references.
  • Validate user-generated data.
  • Separate public and private profile information.
  • Apply Firestore Security Rules.
  • Use transactions for operations that require atomicity.
  • Create appropriate indexes for search queries.

09. Security and Privacy

Authentication and authorization

  • Use Firebase Phone Authentication and OTP verification.
  • Verify identity on the server for privileged operations.
  • Allow users to manage only their own records.
  • Protect admin actions with trusted role checks.
  • Restrict chat reads and writes to authorized participants.

Public/private profile separation

Public responses must contain only explicitly approved fields. Private information can include phone numbers, addresses, guardian contact details, restricted family information and private documents.

Critical technical note: Firestore Security Rules cannot redact selected fields from a document returned by a read. Use separate public/private documents or a trusted server-side API/Cloud Function that constructs an explicit public DTO. More restrictive rules alone do not implement field-level projection.

Contact reveal policy

  1. Confirm the requester is authenticated.
  2. Confirm the requester is a participant in the relevant match.
  3. Verify the match is in an authorized active state.
  4. Verify any required consent and privacy conditions.
  5. Return only the fields the requester is permitted to see.

Secure development practices

  • Never expose Firebase Admin credentials to the client.
  • Never commit .env.local or service-account files.
  • Never trust client-side role information.
  • Validate request payloads on the server.
  • Apply rate limits to sensitive operations.
  • Keep dependencies and security documentation updated.

11. Installation and Setup

Prerequisites

  • Node.js version compatible with the project's Next.js requirements.
  • npm and Git.
  • Firebase CLI.
  • Java 21 for the configured Firebase Emulator workflow, if required.

Clone and install

git clone <YOUR_REPOSITORY_URL>
cd shuvo-milon-matromonial-site
npm install

Configure local environment

# macOS / Linux
cp .env.example .env.local

# Windows PowerShell
Copy-Item .env.example .env.local

Populate the local file using the exact variable names in .env.example and docs/SETUP.md.

Run development server

npm run dev

Open http://localhost:3000.

Run quality checks

npm run lint
npx vitest run
npm run build

Run Firestore rules tests

firebase emulators:exec --only firestore "npx vitest run --config vitest.rules.config.mjs tests/rules --reporter=verbose"

Do not report emulator tests as passed unless the command actually executes and produces passing output.

12. Environment Configuration

Use .env.example as the authoritative list of environment variable names. Configuration categories include Firebase client settings, trusted server-side Firebase Admin settings, Cloudinary signed-upload settings, application environment and development-only mock flags.

Never place real credentials in README or commit local secrets. Restrict API keys, separate development and production configuration, and keep server-only secrets out of browser bundles.
